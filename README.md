# 페이지프렌즈 (pagefriends)

AI 웹사이트 제작 SaaS. 템플릿(데모 1,000원 / 운영 사이트 8,900원) 또는 프롬프트만으로 사이트를 만들고,
완성된 페이지 캡처 위에 **빨간 네모**를 그려 AI 반영·전문가 수정을 요청한다. 3~7일 안에 완성.

- Next.js 16 (App Router) · Tailwind v4 · Supabase (Auth + Postgres, `@supabase/ssr`) · 포트원 V2 (PG: 토스페이먼츠)
- 디자인은 [Design Pickle](https://designpickle.com) 을 벤치마킹: 짙은 네이비 바탕 + 하늘색 액센트 알약 버튼, 작은 대문자 눈썹 라벨 + 큰 굵은 헤드라인, 어두운/흰 섹션 교차, 큰 숫자 통계, 해시태그 칩, 4단계 커맨드 센터, 비교표, 좌(어두운 브랜드 패널)/우(흰 폼) 로그인. 색은 네이비·파랑·하늘색 + 무채색만. 폰트 Pretendard. 버튼은 알약, 카드는 12~16px.

## 1. 로컬 실행

```bash
npm install
cp .env.example .env.local   # 값 채우기 (아래 2·3 참고)
npm run dev                  # http://localhost:3000
```

Windows 에서 `An Application Control policy has blocked this file ... next-swc.win32-x64-msvc.node` 오류로 서버가 뜨지 않으면
(보안 정책이 Turbopack 의 네이티브 파일을 막은 경우) `npm run dev -- --webpack`, 빌드는 `npx next build --webpack` 으로 실행한다.

Supabase 없이도 볼 수 있는 화면: `/` 메인, `/pricing` 요금제, `/demo` **편집 화면 체험**(드래그·휠 줌·네모 그리기·요청 작성).
그 외(`/templates`, 로그인, 대시보드, 결제)는 Supabase 설정이 필요하다.

## 2. Supabase 설정

1. 프로젝트 생성 → Settings > API 에서 URL, anon key, service_role key 를 `.env.local` 에 넣는다.
2. SQL Editor 에서 `supabase/migrations/0001_init.sql` → `0002_admin.sql` → `0003_subscription_lifecycle.sql` → `0004_tokens_sites.sql` → `0005_inquiries.sql` → `0006_messages.sql` → `0007_releases.sql` → `0008_ai.sql` → `0009_billing_cycle.sql` → `0010_bug_ai.sql` → `0011_site_db.sql` 순서로 실행 → 이어서 `supabase/seed.sql` 실행(템플릿 10개).
3. Authentication > Providers
   - Email: 켜기. 로컬 테스트는 "Confirm email" 을 꺼야 가입 즉시 로그인된다.
   - Google: Client ID/Secret 입력. Google Cloud 콘솔의 승인된 리디렉션 URI 에 `https://<ref>.supabase.co/auth/v1/callback` 추가.
4. Authentication > URL Configuration
   - Site URL: `http://localhost:3000` (운영은 실제 도메인)
   - Redirect URLs: `http://localhost:3000/auth/callback`, `https://<도메인>/auth/callback`

### 관리자 지정

가입한 계정을 관리자로 만들려면 SQL Editor 에서:

```sql
update public.profiles set role = 'admin' where email = '<이메일>';
```

관리자는 `/admin` 에서 수정 요청을 묶음별로 보고 사용자에게 답한다. 상태는 저절로 바뀌고(아래 "요청 · 프로젝트 상태"), 예외일 때만 콤보로 직접 고친다.
글과 상태 변경은 요청마다 대화로 쌓여 사용자의 "요청 내역" 과 알림에 보이고, 사용자는 거기에 답글을 단다 (아래 "사용자 ↔ 관리자 대화").
관리자 쓰기는 `admin_*` RPC 로만 가능하며 DB 가 역할을 검사한다.

## 3. 포트원 V2 (토스페이먼츠)

1. 포트원 콘솔 > 결제 연동 > 토스페이먼츠 채널 추가(테스트 채널로 시작) → `NEXT_PUBLIC_PORTONE_STORE_ID`, `NEXT_PUBLIC_PORTONE_CHANNEL_KEY`
2. 콘솔 > API 키 > V2 API Secret → `PORTONE_API_SECRET`
3. 콘솔 > 웹훅 > URL `https://<도메인>/api/webhooks/portone`, 시크릿 → `PORTONE_WEBHOOK_SECRET`
4. `APP_ENCRYPTION_KEY` 에 32자 이상 임의 문자열(빌링키 암호화)
5. 정기결제(구독)는 **빌링키** 방식이라 토스페이먼츠 채널에서 빌링키 발급이 가능해야 한다(계약 필요).

키가 없을 때는 `.env.local` 에 `PAYMENTS_MOCK=true` 를 두면 포트원 없이 결제가 성공 처리된다(개발 전용, production 에서는 무시됨).

### 앱 영역의 어두운 톤 (theme-dark)

대시보드·편집기·결제·관리자는 `app/globals.css` 의 `.theme-dark` 스코프 안에 있다. 이 스코프는 ink 계열·`surface`·연한 틴트(brand-50, sky-50, red-50 등) 토큰만 반전시키므로
페이지 코드는 흰 바탕과 같은 클래스(`bg-surface`, `text-ink-900`, `border-ink-200`)를 그대로 쓴다. 앱 영역에서는 `bg-white` 대신 반드시 `bg-surface` 를 쓰고,
`bg-ink-900` 위 글자는 `text-white` 가 아니라 `text-ink-50` 을 써야 반전 후에도 대비가 유지된다.

### 편집기 동작

- 이미지와 네모를 한 래퍼에 두고 래퍼에 `translate + scale` 을 건다. 네모 좌표는 **이미지 픽셀** 기준이므로 휠 줌을 해도 네모가 이미지와 같이 커지고 작아진다. 테두리·번호·핸들만 `1/zoom` 으로 역보정해 화면 크기를 유지한다.
- 도구: 이동(V) / 빨간 네모(R). 네모 hover 시 8방향 핸들로 크기 조절, 드래그로 이동, Delete 로 삭제.
- 왼쪽 디바이스(모바일·태블릿·웹)는 플랜이 허용하는 것만 활성. 아래 탭은 페이지 경로(홈, 안내, 리뷰, 상품, 관리자페이지…).
- 네모 하나 = 요청 하나. 캔버스의 N번 빨간 네모와 오른쪽 패널의 N번 카드가 1:1 이고, 카드/네모에 마우스를 올리면 서로 강조된다. 종류는 네모마다 따로 고른다 (AI 반영 · 전문가 요청 · 오류 신고).
- "요청하기"는 모든 페이지·디바이스의 네모를 한 묶음(batch)으로 보낸다. DB 함수 `submit_change_requests` 가 한도 검사 → 크레딧 차감 → 삽입을 한 트랜잭션으로 처리한다.

## 요금제 (0009_billing_cycle.sql)

- 플랜 3개, 월간 · 연간 결제 (`config/plans.ts`, 금액은 부가세 포함): 스타터 19,800원 · 비즈니스 29,800원 · 프로 49,800원 / 월. **연간 = 월 요금 × 10** (2개월 무료).
  엔터프라이즈는 요금제에서 빼고 "별도 상담" (`hidden`, 예전 구독을 읽을 때만 쓴다).
- 금액 · 적용 방식은 `lib/billing-quote.ts` 의 `quoteChange` 하나로 계산한다 (결제 화면 미리 보기와 서버 결제가 같은 함수):
  처음 시작 = 바로 결제 · 올리기(상위 플랜, 월간 → 연간) = 남은 기간만큼 빼고 바로 결제, 오늘부터 새 기간 ·
  내리기 · 연간 → 월간 = 다음 결제일부터 (`subscriptions.pending_plan_code` / `pending_billing_cycle` 에 적어 두고 갱신 결제가 그 금액으로 나간다).
- 결제 시스템(쇼핑몰 결제) 연동비 `PAYMENT_SETUP_FEE_KRW`(20만 원)는 처음 켤 때 한 번만 (`subscriptions.payment_addon`).
- "전문가에게 맡기기"(사람이 처음부터 제작)는 연간 결제에만 (`expertBuildIncluded`). 월간은 AI 로 시작한다 — 위저드와 `createProjectAction` 이 같이 막는다.
- 연간 결제 중도 해지 환불(약관): 결제 금액 − 이용한 개월 수 × 월간 요금. 지금은 담당자가 포트원 관리 화면에서 직접 부분 취소한다.
- 0009 전 DB 에서도 월간은 그대로 동작한다 (`activate_subscription` · `submit_change_requests` 를 예전 인자로 다시 부름). 연간 · 예약 변경은 0009 이후.

## 사용량 모델 (0004_tokens_sites.sql → 0009)

- **사이트 수**: 플랜별 동시 보유 사이트 수 (스타터 1 · 비즈니스 2 · 프로 5, `Plan.maxSites`). `createProjectAction` 이 검사하고 대시보드가 남은 슬롯을 보여준다.
- **사용 기간** (`usage_window(user_id)`, 0009): 결제 기간 시작일부터 한 달씩 센 "지금이 속한 달". 월간이면 결제 기간과 같고, 연간이면 1년 안에서 매달 다시 채워진다.
- **AI 반영 = 토큰**: 플랜별 월 토큰 한도 (`Plan.monthlyAiTokens`, 사용 기간 기준). 제출 시점에는 남은 토큰(한도 − 사용 + 크레딧)이 0 이면 막기만 하고,
  처리 시점에 `record_ai_usage(request_id, tokens, monthly_limit)` 로 실제 사용 토큰을 기록하면서 한도 초과분을 토큰 크레딧에서 차감한다.
  지금은 관리자 요청 상세의 "사용 토큰" 칸으로 기록하고, AI 파이프라인이 붙으면 같은 RPC 를 service role 로 호출한다. 사용량 조회는 `ai_token_usage(user_id)`.
- **전문가 요청 = 월 횟수** (`Plan.monthlyExpert`: 1 · 2 · 4, 사용 기간 기준 `request_usage(user_id)`). 초과분은 횟수 크레딧에서 제출 시 차감.
- **오류 신고 (`kind = 'bug'`)**: 무료. 한도·크레딧·토큰 어디에서도 차감하지 않는다.
- 크레딧 팩: AI 는 토큰(1만 토큰 180원 · 10만 토큰 1,400원), 전문가는 횟수(1회 8,900원 · 10회 64,900원). `credits.kind='ai'` 의 balance 는 토큰 수.
- 저장 좌표는 0~1 정규화 값이라 캡처를 다시 찍어 크기가 바뀌어도 위치가 유지된다.

## 사용자 ↔ 관리자 대화 (0006_messages.sql)

- **요청 대화**: 네모(요청) 하나마다 대화가 하나다. 관리자가 상태를 바꾸거나 글을 보내면 그 요청의 대화에 쌓이고, 사용자는 "요청 내역" 에서 요청마다 답글을 단다.
  답글은 토큰·횟수를 차감하지 않는다. 네모 미리보기와 번호를 같이 보여 어느 네모의 대화인지 섞이지 않는다.
- **확인 필요** (`change_requests.awaiting_user`): 관리자가 질문하며 "사용자의 답이 필요합니다" 를 켜면 사용자 화면에 "확인 필요" 로 뜬다. 사용자가 답글을 달면 자동으로 풀리고
  그 요청이 관리자의 "할 일" 로 돌아온다. 작업 상태(status)와 따로 둔다 — 상태는 "일이 어디까지 갔나", 이 값은 "누구 차례인가".
- **사이트 메시지**: 네모와 상관없는 대화 (`messages.request_id` 가 null). 사용자는 `/projects/[id]/messages`, 관리자는 `/admin/messages`. 프로젝트 상태를 바꾸면 안내가 자동으로 남는다.
- **읽음·알림**: `messages.read_at` 은 상대편이 읽은 시각이다. 화면에 실제로 뜬 글만 읽음 처리한다 (`components/messages/mark-read.tsx`).
  사용자: 상단 종 아이콘 + 대시보드 "확인할 내용" + 사이트 카드·편집기 상단의 숫자. 관리자: 상단 메뉴의 숫자 + "할 일" 탭 + "새 답글" 표시.
  숫자는 `/api/notifications` 를 주기적으로 불러 갱신하고, 대화 화면은 보고 있는 동안 20~45초마다 새로 받는다 (웹소켓 없음).
- **쓰기는 DB 함수로만**: `post_message` · `mark_messages_read` (사이트 소유자), `admin_reply_request` · `admin_update_batch` · `admin_post_message` · `admin_mark_messages_read` (관리자).
  읽기는 RLS 로 소유자와 관리자만. 알림 수는 `my_message_summary()` · `admin_message_summary()`.
- **0006 적용 전 DB** 에서는 대화 기능만 꺼지고 나머지는 예전처럼 동작한다 (답변 한 줄 저장). 관리자 화면에 적용 안내가 뜬다.

### 구독 수명주기 (lib/subscriptions.ts)

- **활성화**: 빌링키로 첫 달 결제 → `activate_subscription` → 다음 달 결제를 포트원에 예약(`next_payment_id`, `portone_schedule_id` 저장). 예약 결제용 `payments` 행을 pending 으로 미리 만들어 웹훅이 금액을 대조한다.
- **갱신 성공** (웹훅 `Transaction.Paid`, paymentId `pf_sub_*`): 기간 1개월 연장, 실패 카운터 초기화, 다음 달 재예약.
- **갱신 실패** (`Transaction.Failed`): 상태 `past_due`, 3일 뒤 재시도 예약. 3회 연속 실패면 `cancelled` + 빌링키 삭제. 실패 후 7일 유예 동안은 서비스 이용 가능(`PAST_DUE_GRACE_DAYS`).
- **해지**: 예약만 취소하고 `cancel_at_period_end = true`. 기간 끝까지 이용 가능, 그 전엔 "해지 취소"로 되돌릴 수 있다.
- **결제 수단 변경**: 새 빌링키 발급 → 저장. 미납 상태면 즉시 재결제, 아니면 다음 예약을 새 카드로 교체. "지금 다시 결제"는 등록된 카드로 즉시 시도.
- **만료 판정은 읽는 쪽**(`effectiveSubscription`)에서 한다 — 크론이 없어도 기간이 지나면 플랜이 자동으로 비활성이 된다.
- 로컬(`PAYMENTS_MOCK=true`)에서는 결제 페이지의 "갱신 성공/실패" 버튼이 웹훅을 흉내 낸다(`/api/payments/dev/renewal`).

## 웹사이트 적용 · 개발 서버 → 운영 (0007_releases.sql)

편집기에서 요청한 수정은 "반영 완료 · 답변 완료" 가 되어도 바로 실제 웹사이트에 나가지 않는다. 사용자는 "배포" 라는 말을 모르므로 화면에서는 **웹사이트 적용** 이라고 부른다.

- **사용자** (`/projects/[id]/apply`, 편집기 상단 "웹사이트에 적용" · 대시보드 카드 · 요청 내역 배너): 끝난 수정(적용 대기)을 "웹사이트에 적용 요청" 한다. 담당자에게 남길 말은 선택.
  처음 적용은 사이트 전체 **공개**다(담당자가 "제작 완료" 를 눌러야 요청할 수 있다). 진행은 세 단계로만 보인다: 적용 요청됨 → 점검 중 → 적용 완료. 담당자가 확인용 서버에 올리기 전이면 취소할 수 있다.
  요청 내역의 끝난 요청마다 "웹사이트 적용 대기 · 적용 요청됨 · 적용 점검 중 · 웹사이트 적용 완료" 가 붙는다.
- **관리자** (`/admin/releases`, 상단 메뉴 "웹사이트 적용" 숫자 = 손댈 적용 수). 실제 배포는 평소 방법으로 하고 단계마다 기록한다:
  1. **개발 서버에 배포** — 개발 서버 주소를 넣는다(지난 적용 주소가 미리 채워진다). 처음이면 사용자에게 "확인용 서버에서 점검 중" 메시지가 간다.
  2. **개발 서버에서 확인** — 사이트가 열리고 모든 페이지로 이동 · 실린 수정마다 "요청대로 바뀌었다" · 화면(플랜의 모바일/태블릿/웹) 체크.
     **폼·DB 구조 변경**(예: 문의하기에 받을 항목 추가)을 켜면 "개발 DB 에 새 항목을 넣고 폼을 보내 저장 확인" 과 "운영 DB 에 먼저 반영" 이 더해진다. 수정 글이 그런 수정처럼 보이면 켜라고 알려 준다.
     문제가 있으면 **다시 고치기**(문제 기록) → 고친 뒤 개발 서버에 다시 배포 → 확인 목록은 처음부터. 사용자에게는 계속 "점검 중".
  3. **운영에 배포** — 위 확인을 모두 체크해야 열린다. 운영 주소를 넣으면 사용자에게 "적용했어요 + 주소" 메시지가 가고 그 주소가 "내 웹사이트" 로 보인다.
- **건너뛸 수 없다**: 순서와 확인 목록은 DB 함수가 지킨다. 개발 서버를 거치지 않았거나(`NOT_STAGED`) 확인이 남았으면(`CHECKS_INCOMPLETE`) `admin_release_live` 가 거절한다. 사이트마다 진행 중인 적용은 하나뿐이다(유일 인덱스).
- **어떤 수정이 실리나**: `change_requests.release_id`. 요청할 때 끝난 수정을 싣고, 개발 서버에 (다시) 배포할 때 그 사이 끝난 수정도 싣는다(그 빌드에 들어 있으므로).
  적용 전에 수정이 다시 열리면 묶음에서 빠지고, 이미 적용된 수정을 다시 고쳐 끝내면 "적용 대기" 로 돌아온다(트리거 `change_requests_release_sync`).
- 적용 기한은 사람이 맡는 일과 같은 `EXPERT_HOURS`(24~72시간). 표기 · 확인 목록 키는 `config/releases.ts`, 읽기는 `lib/releases.ts`.

## AI 엔진 1단계 — 디자인 유형 · 벤치마킹 · 템플릿 + 하네스 (0008_ai.sql)

AI 는 웹사이트 코드를 통째로 쓰지 않고 **디자인 문서**(`brief.design`: 테마 + 문구 자리)만 고친다. 구성 초안 그림(`lib/draft-render.ts`)이 이 문서로 그려진다.
AI 출력은 정해진 형식(구조화 출력)으로만 받고, 코드가 값 범위 · 키 · 글자 수 · 지어낸 사실을 다시 검사한 뒤 반영한다 — 한 곳을 고쳐도 다른 곳이 깨지지 않고, 같은 형식의 기록이 쌓여 나중에 자체 모델을 학습시키기 좋다.

- **디자인 유형(태그)**: 18개 중 최대 4개, 처음 고른 것이 대표(★). 태그마다 축(여백 · 제목 무게 · 모서리 · 색 · 온도 · 말투) · 글꼴 · 쓸 것 · 피할 것 · 말투가 있고,
  `mergeStyles` 가 대표 가중치 2로 합친다. 반대 축은 "충돌" 로 알려 대표를 따르고 다른 쪽은 포인트에만 쓴다. 위저드 3단계에서 고르고, 첫 화면 미리보기와 "AI가 이렇게 적용해요" 가 바로 바뀐다.
  API 키가 없어도 규칙으로 테마를 만들어 **초안이 태그대로 달라 보인다** (명조 · 여백 · 모서리 · 버튼 · 첫 화면 배치 · 카드 · 다크).
- **벤치마킹(첫 요청 필수)**: 주소 1~3개 · 참고할 점 · 좋았던 점 · **허락 상태**(우리 사이트 / 허락 받음(+어떻게) / 허락 없음 — 분위기만) · 확인 체크(시각 · 문구 저장).
  템플릿으로 시작하면 템플릿(사용 허락 포함)이 첫 벤치마킹이라 주소는 선택. 허락 수준별로 AI 가 참고할 수 있는 범위가 지시서에 들어간다. 사이트 화면을 직접 읽는 기능(SSRF 방어 포함)은 다음 단계.
- **템플릿**: `config/template-designs.ts` 에 태그 · 테마 · 구성. 위저드에서 고르면 태그 · 메인 색 · 테마가 미리 채워지고, 편집기의 AI 반영 네모마다 **참고 템플릿**(구매한 것만)을 붙일 수 있다. `/templates` 에 디자인 유형 필터.
- **네모별 옵션**: AI 반영 네모마다 디자인 유형 · 참고 템플릿 → `change_requests.options` (submit_change_requests 가 저장 · 템플릿 구매 확인).
- **하네스**(`lib/ai/harness.ts`): system[0] 기본 규칙 + 정책 스킬(지어낸 사실 금지 · 연락처 · 실제 사진 · 자료/지시 구분 · AI 티 피하기) → system[1] 이 사이트의 스킬(디자인 유형 · 업종 · 시작 템플릿 · 벤치마킹) → user(고객 자료 · 문구 자리 · 요청 글 · 네모 · 네모별 옵션). 두 system 블록은 캐시한다.
  관리자 `/admin/projects/[id]` **AI 작업 지시서** 에서 합친 결과 · 스킬 · 실제 지시문 전체 · 실행 기록을 본다.
- **엔진**(`lib/ai/engine.ts`, 키가 있을 때): 위저드 "AI로 바로 만들기" 뒤 `after()` 로 첫 제작(토큰 차감 없음 · 사용자당 하루 2번) / "요청하기" 뒤 AI 반영 네모를 차례로 처리 →
  `apply` 디자인 새 버전 + 캡처 다시 그리기 + **네모 위치 옮기기**(그림 높이가 바뀌어도 네모가 같은 곳을 가리키게) + "AI가 반영했어요" 대화 + 토큰 기록 /
  `ask` 사용자에게 질문(확인 필요, 답하면 이어서) / `expert` 담당자에게 넘김. 이미지 생성 요청은 담당자가 처리. 쓰기는 `ai_apply_design` · `ai_finish_request`(service role 전용)가 한 트랜잭션으로.
  AI 반영은 담당자 확인 없이 편집기 화면에 바로 반영된다 (실제 웹사이트 적용은 따로 "웹사이트 적용" 흐름).
- **AI 작업 중 화면**: "요청하기" 로 보낸 묶음을 엔진이 **하나씩 순서대로**(페이지 순서 → 화면 → 네모 번호, AI 반영 다음 오류 신고) 처리하고,
  편집기는 1초마다 `GET /api/projects/[id]/ai-progress?batch=` (`lib/ai/progress.ts`)로 진행을 읽는다. 네모마다 가리키는 곳 · 단계
  (확인 → 고칠 방법 정하기 → 바꿀 내용 쓰기 → 새 화면 그리기, `ai_runs.output.live`) · 걸린 시간 · AI 설명(답을 쓰는 동안 먼저 도착)을 보여 주고,
  하나 반영될 때마다 화면을 바로 새로 그리며 고치는 네모를 따라 페이지 · 화면을 옮긴다. 그동안 캔버스는 잠긴다 (화면 이동 · 확대만). 새로 고침해도 이어진다.
  AI 에게는 같이 보낸 다른 요청(먼저 반영된 것 · 다음 차례)을 알려 앞 요청을 되돌리거나 다음 요청의 일을 미리 하지 않게 한다.
- **오류 신고 = AI 가 먼저 확인** (`processBugReport`, 0010): 최근 AI 변경(최근 8건) 때문이면 **그 변경만 되돌리고**(그 뒤에 다시 바뀐 값은 두고, 되돌린 실행에는 평가 "잘못함"),
  테마 · 문구로 고칠 수 있는 화면 문제면 고치고 → "고침 완료". 기능 · 사진 · 구조처럼 할 수 없거나 확신이 없으면 "담당자 확인 중" 으로 넘기고 **24시간**(`BUG_HOURS`) 안에 관리자가 고친다.
  오류 신고는 무료(토큰 차감 없음). AI 작업 중 화면이 끝나면 결과마다 "이상해요 · 오류 신고" 로 그 자리에 오류 신고 네모를 바로 만들 수 있다.
  키 없이 흐름을 시험할 때는 가짜 API 서버를 띄우고 `.env.development.local` 에 `ANTHROPIC_API_KEY` · `ANTHROPIC_BASE_URL` 을 잠깐 넣는다 (SDK 가 읽는다. 끝나면 지운다).
- **비용**: Claude Opus 5.5 (`config/ai.ts`). 사용자 토큰 차감 = 실제 비용을 입력 토큰 단위로 바꾼 값(입력 1 · 캐시 쓰기 1.25 · 캐시 읽기 0.05 · 출력 5). 하루 전체 비용 상한 `AI_DAILY_BUDGET_USD`(기본 30달러).
  안전 거절에 대비해 서버 쪽 대체 모델(`fallbacks: "default"`)을 켰다. 10분이 지나도 끝나지 않은 처리, 요청하고 30분이 지나도 AI 가 손대지 못한 접수(`AI_QUEUE_MINUTES`)는 이유를 남기고 담당자에게 넘긴다.
- **기록 · 학습**: 실행마다 `ai_runs`(지시서 버전 · 입력 요약 · 출력 · 반영한 변경 · 토큰 · 비용). 관리자가 "잘함 · 잘못함 · 고쳐서 마무리" 로 평가해 정답 · 오답 데이터를 남긴다.
  학습에 쓰기 전에 개인정보를 가명 처리하고, 약관 · 개인정보 처리방침에 AI 처리(국외 이전: Anthropic) · 서비스 개선 활용을 적어야 한다.
- 키가 없거나 0008 이 없으면 AI 를 부르지 않는다 — 화면은 그대로, AI 반영은 담당자가 처리한다.

### 아직 연결하지 않은 것 (다음 단계)

- 실제 AI 사이트 생성·캡처 파이프라인: 지금은 위저드 입력으로 그린 **구성 초안**(`/api/drafts/…`)을 캡처 자리에 넣는다 (예전 사이트는 샘플 SVG). 실제 캡처 URL 과 크기(+ 이미지 자리 위치 `slots`)만 넣으면 편집기는 그대로 동작한다.
- 실제 AI 이미지 생성: 위저드에서 고른 자리는 AI 반영 요청으로 접수되고, 지금은 담당자가 만들어 넣은 뒤 사용 토큰을 기록한다. 이미지 생성 API 를 붙이면 같은 요청을 처리하면 된다.
- 결제 실패·해지 알림 메일: 지금은 결제 페이지 배너로만 알린다.
- 대화 알림 메일 · 푸시: 새 답변·메시지는 로그인했을 때 화면 안에서만 알린다. 메일 발송 수단(SMTP · 메일 API)을 붙이면 `admin_reply_request` · `post_message` 호출 뒤에 보내면 된다.
- 대화에 파일 첨부: 대화는 아직 글만 주고받는다. 이미지 자리에 넣을 사진은 "실제 사진 올리기"(아래)로 받는다.
- AI 2단계: 실제 웹사이트(HTML) 렌더러 · 구역 추가/삭제 같은 구조 변경 · 버전 되돌리기 화면 · 작업 대기열(지금은 after()) · 벤치마킹 사이트 읽기 · 이미지 생성 API. 3단계: ai_runs 로 평가셋 → 자체 모델 파인튜닝 → 쉬운 요청은 자체 모델로 보내는 라우터.
- 실제 배포 자동화: 웹사이트 적용은 담당자가 배포한 뒤 단계를 기록한다. 고객 사이트 호스팅의 배포 훅(예: Vercel Deploy Hook)을 붙이면 "개발 서버에 배포" · "운영에 배포" 버튼이 직접 배포하고 주소를 받아 오게 바꿀 수 있다 (`admin_release_staging` · `admin_release_live` 는 그대로).

## 사이트 전용 Supabase · 관리자 목록 · 관리자 페이지 (0011_site_db.sql)

고객이 사이트를 만들면 **그 사이트만 쓰는 Supabase 프로젝트**를 관리 API 로 자동으로 만든다 (`lib/site-db`). AI 에게 "이 페이지를 목록으로 만들고 관리자 페이지에서 관리하게 해 주세요" 라고 요청하면
AI 가 **관리자 목록**(공지 · 메뉴 · 상품 …)을 만들고 → 그 프로젝트에 표가 생기고 → 사이트 주인의 **관리자 페이지**(`/projects/[id]/admin`)에 저절로 나타난다.

- **설정** (`.env.local`): `SUPABASE_ACCESS_TOKEN`(대시보드 > Account > Access Tokens. 범위 제한 토큰이면 리소스는 조직 전체 · 권한은 Full access — 프로젝트 하나만 고르면 새 프로젝트를 못 만든다. 만료가 최대 1년이니 그 전에 바꿔 넣는다) + `APP_ENCRYPTION_KEY`(32자 이상, 키를 암호화해 둔다) + `SUPABASE_SERVICE_ROLE_KEY`.
  조직은 `SUPABASE_SITES_ORG`(비우면 앱 메인 프로젝트가 있는 조직), 지역은 `SUPABASE_SITES_REGION`(비우면 서울). `SITE_DB=off` 면 만들지 않는다.
  **무료 조직은 계정당 2개까지**라 운영에서는 조직을 Pro 로 올려야 한다 (프로젝트마다 Micro 약 $10/월). 무료 프로젝트는 1주일 동안 쓰지 않으면 멈춘다.
- **언제 만드나**: 위저드 제출 뒤 백그라운드(`after`) — 플랜이 있고 `Plan.siteDatabase` 가 켜진 플랜만 (`config/plans.ts`, 지금은 모든 플랜). 플랜 없이 만든 사이트 · 예전 사이트는
  AI 가 목록을 처음 만들 때, 관리자 페이지를 열었는데 목록이 있을 때, 담당자가 관리자 "제작 정보" 에서 "만들기" 를 누를 때 만든다.
  상태는 `site_databases`: creating → provisioning(켜지는 중, 보통 1~3분) → ready(키를 받아 암호화 저장) / failed(이유 · 담당자 "다시 시도"). 같은 사이트에 두 개가 생기지 않게 행 하나를 조건부로 맡고,
  만들다 끊기면 이름 `pf-<사이트 id 앞 8자리>-…` 로 이미 생긴 프로젝트를 찾아 이어 쓴다. 사이트 행이 지워져도 이 행은 남는다 (지울 프로젝트를 찾을 수 있게).
- **관리자 목록** (`lib/collections.ts`, 디자인 문서 `collections`): 목록 = 표 하나. 키는 영어 소문자 · 숫자 · 밑줄, 칸 종류는 짧은 글 · 긴 글 · 숫자 · 날짜 · 예/아니오 · 링크 · 사진 주소 · 이메일 · 전화번호.
  모든 표에 id · 만든 시각 · 고친 시각 · 공개(published) · 순서(sort)가 자동으로 있다. AI 는 정해진 형식(`EditOutput.collectionChanges`)으로만 보내고 **SQL 을 쓰지 않는다** —
  코드가 키 · 종류를 다시 검사한 뒤 정해진 규칙으로 SQL 을 만든다(`planSchemaSync`: 새 표 + 공개된 줄만 누구나 읽는 RLS + 새 칸). 표 · 칸은 늘어나기만 한다: 목록이나 칸을 빼면 화면에서 숨길 뿐 글은 지우지 않고,
  이미 있는 칸의 종류는 바꾸지 않는다. 실행한 SQL 은 `site_db_changes` 에 남는다. AI 작업 중 화면에는 "관리자 페이지 만들기" 단계로 보인다. 오류 신고의 되돌리기는 관리자 목록을 되돌리지 않는다.
- **관리자 페이지**는 비즈니스 플랜부터 (`Plan.cms`). 스타터의 목록 요청은 AI 가 플랜을 안내하고 묻는다. 글 읽기 · 쓰기는 서버가 사이트 프로젝트의 Data API 를 비밀 키로 부른다 (`lib/site-db/data.ts`) —
  표 · 칸은 실제로 만든 것(`site_databases.schema`)만 쓴다 (디자인 문서는 사이트 주인이 직접 고칠 수 있어서 그것만 믿지 않는다).
- **구성 초안**: 목록이 붙은 페이지는 공개된 글을 읽어 함께 그린다 (게시판형 5줄 · 카드형 3장). 글 수와 상관없이 그림 높이가 같아 네모 위치가 흔들리지 않는다.
  공지 · 블로그 · 자주 묻는 질문 페이지는 원래 빈 목록 대신, 다른 페이지는 본문 아래(아래 행동 유도 띠 앞)에 그린다.
- 관리자 "제작 정보" 에 상태 · Supabase 대시보드 링크 · 만들기/다시 시도 · 표 다시 맞추기 · 목록이 보인다.

## 새 사이트 위저드 · 구성 초안 · 이미지 자리

결제한 고객이 처음 거치는 화면 (`/projects/new`). 웹사이트를 처음 만드는 사람과 잘 아는 사람이 같은 입력을 만든다.

- **0 시작**: "처음이에요"(쉬운 모드: 설명 상자 · 선택 항목 접기) / "잘 알아요"(직접 구성: 페이지 종류 · 페이지별 메모 · 이미지 설명 고치기). 언제든 바꿀 수 있다.
  **누가 만들까요**: "AI로 바로 만들기"(구성 초안 즉시) / "전문가에게 맡기기"(`EXPERT_HOURS` 24~72시간 안에 첫 완성본, `brief.site.builder`). 설명만으로 / 구매한 템플릿으로.
- **1 회사 · 서비스**: 회사 이름 · 업종(칩 12종 또는 직접 입력 → 분류 추정) · 한 줄 소개(첫 화면 제목) · 제공하는 서비스·상품·솔루션(최대 8) · 하고 싶은 일(문의·예약·판매…) · 강점 · 주요 고객 · 연락처 · 회사 소개 글.
- **2 메뉴 · 페이지**: 업종 · 목적 · 서비스 · **플랜 페이지 수**(스타터 5 · 비즈니스 12 · 프로 30, 홈 포함)에 맞춘 추천 구성에서 시작한다(`recommendMenu`). 헤더 미리보기, 메뉴 순서·이름, **하위 페이지**(하위 페이지가 있는 메뉴는 자기 페이지가 없고 첫 하위 페이지로 간다), 자주 쓰는 메뉴 칩, 필요한 기능(페이지에서 자동 + 직접 선택).
- **3 디자인**: 톤 · 메인 색상(헤더 미리보기에 바로 반영) · 참고 사이트 · 추가 요청.
- **4 이미지**: "AI로 이미지 만들어 넣기" 체크. 켜면 **토큰을 많이 쓴다는 안내** + 예상치(장 수 × `APPROX_TOKENS_PER_IMAGE`, config/plans.ts, 지금 2만) + 남은 토큰 대비 %. 남은 토큰(한도 + 크레딧)보다 많으면 다음으로 못 간다(서버도 검사). 끄면 자리를 비워 두고 **자리마다 어떤 이미지가 필요한지** 적어 둔다. 대표·구성원·건물·상품·메뉴·작업물처럼 실제여야 하는 자리(`source: "real"`)는 켜도 AI 로 만들지 않는다.
- **5 확인** → 제작 시작. 입력은 브라우저에 임시 저장돼 새로 고침해도 이어서 쓸 수 있다.

만들 때 일어나는 일 (`createProjectAction`):

1. `buildSitePlan` 이 메뉴 → 실제 페이지(하위 페이지 포함, 주소 자동) → 이미지 자리 목록을 만든다. 결과는 `projects.brief.site`, 회사 정보는 `brief.business` (jsonb 라 **마이그레이션 없음**).
2. 페이지마다 화면별 **구성 초안**을 그려 캡처 자리에 넣는다: `screenshots[device] = { url: /api/drafts/{pageId}/{device}, width, height, draft: true, slots: [이미지 자리 위치] }`. 그림은 요청 때마다 brief 로 다시 그린다(RLS 로 주인·관리자만).
3. AI 로 만들기로 고른 자리마다 **AI 반영 요청**을 그 자리 위치에 한 묶음으로 접수한다(`submit_change_requests`). 토큰은 다른 AI 요청처럼 처리할 때 `record_ai_usage` 로 기록된다.

편집기에서: 왼쪽 페이지 목록이 메뉴 묶음대로 들여 써지고, 상단에 "구성 초안" 표시, 오른쪽 위 **"이 페이지의 이미지 자리"** 목록(상태 · 필요한 이미지 · 권장 크기). 항목에 마우스를 올리면 캔버스에서 그 자리가 강조되고, 누르면 그 자리로 이동한다. **"AI로 만들기"** 는 그 자리에 AI 반영 네모와 요청 글을 채워 준다(보내기 전에 고칠 수 있다).
관리자는 `/admin/projects/[id]` "제작 정보"에서 회사 정보 · 메뉴 구성(페이지 종류 · 메모) · 이미지 자리 전체를 본다. 사용자는 편집기 상단 "제작 정보"에서 같은 내용과 준비할 사진 목록을 본다.

## 요청 · 프로젝트 상태 (저절로 바뀌고, 예외만 콤보로)

- **AI 반영**은 요청하면 바로 AI 차례다: 접수 = "AI 진행 중"(AI 가 처리하거나, 질문해 두고 답을 기다림), AI 가 맡지 못해 담당자에게 넘기면 "담당자 확인 중", 끝나면 "반영 완료"
  (`requestStatus(kind, status)`, config/requests.ts). 넘길 때는 AI 가 이유를 대화에 남긴다 (lib/ai/engine.ts).
- **전문가 요청 · 오류 신고**는 사람이 24~72시간 안에 답한다 (`EXPERT_HOURS`, config/plans.ts). 사용자 화면에 "답변 기한 · 10월 18일 …까지", 관리자 목록·상세에 "답변 기한 N시간 남음/지남".
  - 접수 → 담당자가 요청 화면을 **열면** 자동으로 "확인 완료" (`AutoCheck` → `markRequestCheckedAction`, 대화에 "담당자가 요청을 확인했습니다").
  - 담당자가 **답변을 보내면** 자동으로 "답변 완료". "사용자 답 필요(질문)" 를 체크하면 "확인 완료" 로 남는다.
  - 예외(반영 불가 · 되돌리기)는 답변 폼의 상태 콤보 · 목록의 "묶음 전체 직접 고치기" 로 고친다. 콤보에서 고르면 "직접 고름" 이 자동보다 우선하고, "자동으로 되돌리기" 로 돌아간다.
- **프로젝트**: 만들면 "제작 중" → 담당자가 **"제작 완료" 버튼**을 누르면 "제작 완료"(사용자에게 메시지). 완료 뒤 새 수정 요청이 오면 "수정 반영 중"(DB 함수), 열린 요청을 모두 처리하면 저절로 "제작 완료" 로 돌아온다. 예외는 "직접 고치기" 콤보.

## 실제 사진 올리기 (Supabase Storage)

- 이미지 자리마다 고객이 사진을 올린다: 편집기 오른쪽 "이 페이지의 이미지 자리", 제작 정보(`/projects/[id]/brief`), 관리자 제작 정보. 올린 사진은 편집기 캔버스에서 그 자리 위에 겹쳐 보인다.
- 저장: 비공개 버킷 `site-photos` (처음 올릴 때 서비스 롤로 자동 생성, 2026-10-15 생성 완료). 파일 이름이 곧 기록이라 DB 테이블·마이그레이션이 없다: `{projectId}/{자리 id base64url}.{uuid}`.
- 권한: `/api/projects/[id]/photos`(목록 · 올리기 · 지우기), `/api/projects/[id]/photos/[name]`(보기 → 1시간짜리 저장소 주소로 넘김). 프로젝트를 RLS 로 읽어 보고 주인 · 관리자만 허용한다.
- 브라우저가 2000px 이하 JPEG 로 줄여 한 장씩 보낸다(위치정보 제거). 서버는 첫 바이트로 JPG · PNG · WEBP 만 받고, 자리의 장 수(`count`)를 넘지 않게 막는다. 여러 장을 올리면 마지막 장에서 한 번만 담당자에게 사이트 메시지로 알린다.
- `next.config.ts` 의 `experimental.proxyClientMaxBodySize` 를 20MB 로 올렸다 (proxy 가 본문을 기본 10MB 에서 조용히 자른다).

## 공개 사이트 (디자인 피클 구조)

공개 페이지는 designpickle.com 의 정보 구조를 페이지 단위로 그대로 옮겼다 (헤더 메가메뉴 · 푸터 · 홈 · 플랫폼 · 요금제 · 이용 방법 · 비교 · 솔루션 14종 · 작업 사례 · 고객 사례 · 블로그 · 리소스 · 회사 소개 · 팀 · 채용 · 전문가 지원 · 실시간 채팅 · 상담 신청 · 도움말 · 약관 · 검색).

- 콘텐츠는 `content/site.ts` 한 곳에 있다. 내비 · 푸터 · 솔루션 · 후기 · 사례 · 글 · 팀 · 채용 · FAQ 전부.
- 사진은 전부 임시다. `node scripts/gen-placeholders.mjs` 가 `public/placeholders/*.svg` 와 `config/placeholders.json` 을 만든다. 실제 사진이 오면 같은 파일명으로 바꿔 끼우거나 `content/site.ts` 의 `ph()` 자리를 실제 경로로 바꾼다.
- 후기 · 고객 사례 · 블로그 글 · 팀 · 채용 공고는 `sample: true` 샘플이며 화면에 "샘플" 표시가 붙는다. 실제 콘텐츠로 교체해야 한다. 지어낸 실적 수치(고객 수 · 매출)는 넣지 않았다.
- 상담 신청 · 뉴스레터 · 전문가 지원 · 문의 폼은 `app/actions/inquiries.ts` → `inquiries` 테이블(0005). 관리자 화면 `/admin/inquiries` 에서 본다.
- 섹션 부품은 `components/marketing/primitives.tsx`(서버) · `interactive.tsx`(클라이언트). 헤더는 `components/site/nav.tsx`(메가메뉴 · 검색 · 모바일 드로어).
